## Lessons for future agents
1. **Dedupe is URL-normalisation based** (query strings/utm stripped). Different LinkedIn job IDs for the same role count as distinct postings — near-duplicate titles survive as separate rows.
2. **Never run the merger with a full `inbox/`.** With all ~250 inbox files present, a dry-run showed +4479 incoming rows and thousands slated for archival — that rewrites the whole board and is not an hourly merge. Isolate the current scanner's file (move other `inbox/*.md` out), merge, then restore.
3. **Merger requires absolute `YYYY-MM-DD` posted dates** and real posting URLs; aggregator listing pages and sales/marketing titles are rejected automatically. Undated employer career pages (e.g. Lane Four Salesforce roles) must be held for review, not given invented dates.
4. **Publish order matters:** update README first, then run `tools/build_site.py` so `public/jobs-data.json` and `public/index.html` reflect the merged board. Build from README + `jobs.json` union so a per-table cap can never hide a posting.
5. **Windows/git:** `git` works only with `PATH` prepended `/c/Program Files/Git/cmd` (`/mingw64/bin/git` is denied). Push to GitHub over HTTPS works once rebased onto origin/main.
6. **Fresh Toronto SN/SF volume is low:** 16 candidates found, 15 genuinely new. Most recent Toronto postings are already on the board from earlier scans; partner/employer pages often publish no date and are skipped by the merger. Partner-portal scans (Accenture, Deloitte, KPMG, Capgemini career pages) and Canadian government boards (Region of Peel, federal GC Jobs) are worth checking each cycle but frequently yield undated listings.
